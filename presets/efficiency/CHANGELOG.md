## 0.4.0 — 2026-11-09

主题：**一个预设，多个模式 —— 丢个目录，就多一个能派工的工人。**

### 新增

- 一个预设能带多个模式：丢一个目录进 `modes/`（`mode.yml` + 它自己的 `skills/`）就多一个能派工的模式，不用改配置、不用改代码。**加完要重启一次 DSH —— 注册发生在加载时，v1 不热加载**，不假装这是零成本。
- 派工能挑人了：模型按每个模式的一句话描述决定派谁；派工工具 `dispatch_mode` 的可选值从目录里算出来，默认 `general` —— 少配一个模式不会变成「配了却选不到」。
- 每个模式有自己的技能库：出厂库随预设走，本地积累库在 `<DSH_HOME>/mode-skills/<mode>/`，而且**不继承**工作区/用户级的 skill —— 换一个模式，不会捡到别人攒的私货。
- 用不上的宿主工具可以整段看不见：按前缀把它们从提示词里摘掉，而不是等调用时才拒绝 —— 模型看不到那个工具，就不会围着一个必然失败的调用绕圈。
- 底座的插件清单跟预设行对齐到 19 行，并加了防漂移断言 —— 两边差一行测试立刻红，不靠人记。

### 修复

- 修复：以前加一个模式得同时改 YAML 和代码，漏一处就派不到它；现在目录即声明，可选值跟着目录走，少配、配错不可能再悄悄发生。

## [0.3.6] - 2026-11-08

主题：**回执成章法——六段，缺一项就是不合格。**

### Changed

- 「交付固定三段」升级为**固定六段**，总长 ≤ 40 行：

  | 段 | 内容 |
  |---|---|
  | 一、结论 | 一句话：成 / 不成 / 部分成 |
  | 二、产物 | 每行 `<路径>（<大小/行数>）`，没有写"无" |
  | 三、证据 | 一条可复现命令 + 关键输出 ≤5 行，或"看了哪张图看到了什么" |
  | 四、验收对照 | 任务书第 5 要素逐条：要求 → 达成/未达成/未实现 → 依据 |
  | 五、补正 | 任务书之外做了什么 + 怎么回滚；没有写"无" |
  | 六、遗留与风险 | 卡点、未验证项、假设；没有写"无" |

- 硬规矩一条：**第四段出现「未达成 / 未实现」，第一段结论就必须是「部分成」或「不成」**。
  结论和验收对照打架的回执，等于伪造。

### Why

上游（规划者）验收时拿的是这份回执。回执不成章法，验收就只能靠猜。

## [0.3.5] - 2026-11-08

主题：**把「零提问」和「不许上报」分开——前者是纪律，后者是事故。**

### Why

黑名单里原来写着「执行中途请示 → 零提问是这个模式的全部价值」。这句话被读成「不许开口」，
于是 Agent 卡在阻塞的工具上时，宁愿换假设重试也不说一句。零提问本来只该管**问范围和偏好**，
不该管**报告卡死**。

### Changed

- 黑名单那一行改成：**拿范围 / 偏好 / 方案取舍去打扰上游**才违规；
  **卡死、超时、环境阻塞必须立刻上报——那是通知，不是请示。**
- 新增 **§三·四「什么时候必须上报」**：单次调用 >20s / 同一工具 2 次超时 / 同一假设失败 2 次 /
  环境阻塞第一次 —— 四种触发各给动作，并给了一句话模板。
- 新增 **§三·五 三条省时硬纪律**：一轮只改一个变量 / 沉默不等于失败（只看产物）/
  环境操作节流（刷新与编译各一次）。
- §三·三 补一条：外部编辑器类工具第一次调用前先确认窗口可见且非最小化（最小化时主循环被节流，调用会假死）。

### Note

上报通道是 `send_message`（`tool-subagent-control` 提供，已在工具面里），
可以直接发给派它的那一级，对方会被立刻叫醒。

## [0.3.3] - 2026-11-08

主题：**反打转守卫 + 操作外部系统的流程。**

### Why

实测轨迹：操作 Unity 编辑器的 MCP 工具在编辑器失焦时全部阻塞，单次调用把 `run_code`
拖到 120 秒上限；Agent 换一个假设再来一次，21 步里 8 步在跟同一个阻塞打交道，
中间还夹了 4 次 `recompile`、3 次 `Assets/Refresh`。不是能力问题，是没人提醒它在原地打转。

### Added

- **`guard.js` 反打转守卫（两条，都很窄）**：
  - **慢 MCP 连击**：上一次是 `mcp__*` 且间隔 > `slowGapMs`（20s），这次**又是** `mcp__*` → 拦一次，
    告诉它「工具在阻塞，不是参数问题，换路或上报」。拦一次就放行。
  - **同参数连击**：同一工具 + 同一份参数**连续第 3 次** → 拦一次，给三个选项（换参数 / 换路 / 交回）。
  - 刻意不做：失败预算（守卫看不到结果，会乱杀）、禁止工具（只拦一次）。
- **人格 §三·三「操作外部系统」**：先量一次往返 → 一条链一次验证 → 成功判据只有产物 →
  **失败分三类**（参数错 / 环境阻塞 / 逻辑错，各有各的路）→ 失败台账一行一条 → 三次不同尝试失败就上报。

### Note

守卫只能逼它早点停，救不了阻塞的工具本身。要根治得让外部系统支持后台执行
（Unity 的 `-executeMethod` 或异步句柄）。

## [0.3.2] - 2026-11-08

主题：**你随时可以喊人，不用等到结束。**

### Added

- 新增 **§三·二「你随时可以喊人」**：被派出来不等于关着——`send_message` 直接发给派你的那一级，
  会立刻叫醒它处理，不用等你这轮跑完。

- 发了继续干能干的，不要原地等（上游会用 steer 把决定推回来）。
- 黑名单加一行：「把卡点攒到交付时才说 —— 你省了一次消息，上游白等一整轮」。

### Note

`tool-subagent-control`（send_message / interrupt_agent / list_agents）本就在工具面里，
这次是把「什么时候用它」写成硬规矩。

## [0.3.1] - 2026-11-08

主题：**等待不是重试。**

### Why

实测事故：Unity 编辑器窗口被最小化，抓帧一直拿不到画面。Agent 把它当成"再试一次就好"，
在同一处反复重试，既不成功也不上报——上游看到的是"还在跑"。

根因：原来的「第二次失败就停手」只覆盖**报错**，没覆盖**条件不满足**。
截图返回空不是错误，是环境状态，重试改变不了它。

### Added

- 新增 **§三·一「等待不是重试」**：
  - 轮询硬上限：`maxAttempts ≤ 3`、总超时 ≤ 30 秒，写死在代码里，不许 `while(true)`，不许外层再包循环。
  - 环境状态类失败（窗口最小化 / 焦点不在前台 / 进程没起 / 文件未生成 / 设备被占用）**第一次就上报**，
    并把需要上游做什么说清楚。
  - **不许自己改环境绕过**（强提窗口、模拟按键、切分辨率）。
  - 空白结果先判一次因（可见吗 / 在 Play 吗 / 渲染完了吗），判不出就上报，不靠次数碰运气。
  - **卡住要让上游在三分钟内知道**——沉默地转圈比报错更糟。
- 黑名单新增两行：无限重试抓帧；用 `while(true)` 等外部条件。

## [0.3.0] - 2026-11-07

主题：**把「慢」算清楚**。这一版没有加快任何东西——它改的是这个模式对成本的理解。

### Added

- **§二 重写为「慢的根源是往返次数，不是模型」**
  - 一次模型往返不慢，二十次就是十几分钟；被计价的单位是"来回几趟"，不是"一个任务"。
  - 能一次 `run_code` 做完的，不许拆成三次。
  - 换模型省的是思考预算，省不了 API 往返——杠杆永远是**少跑几趟、每趟多装点**。
  - 判据从"跟自己比快"改成"跟上游自己动手比快"：上游三分钟能干完的机械活，我花五分钟就已经亏了。
- **环境坐标规则（§二 新增）**：找不到 python / exe / 缺库不是任务，是纯成本，能把 3 分钟的链拖成 25 分钟。
  - 开工第一步用一次 `run_code` 把坐标探全（解释器、工具、版本、目录），探到就写进回执。
  - 环境类问题**只允许试一次**，第二次立刻停，报「缺什么 + 我要什么」。
  - 换路优于修路：换路 30 秒，修路可能 30 分钟。
- **§三 修复判据补一条**：环境类问题（找不到解释器、缺库、路径不存在、权限）一律不值得修，直接按坐标规则停手交回。
- **§〇 开工第一步**同时探一次环境坐标；任务书给了就直接用，不许"再确认一下"。
- **§六 黑名单 +4 条**：为环境问题来回啃三次以上 / 每步重探解释器路径 / 把一次能做完的拆成三次往来 / 接了机械活还按内容生产的节奏做。
- **§七 诚实边界 +1 条**：我的速度上限由任务书给的坐标决定，这个慢是上游付钱。

### 为什么这些不算"效率优化"

四条教训里没有一条能靠"换个更快的模型"解决。能动的是三件事：少跑几趟、别啃环境、让上游把不需要派下去的机械活收回去。
最后一条不在本预设的权限范围内——它写在 `dsh-preset-planner` 的 §四。

## [0.2.0] - 2026-11-07

### Added

- 人格新增 **§六 反模式黑名单**（10 条集中表）：把散落在五节的禁令收成一张可查表。
- 人格新增 **§七 诚实边界**（6 条具体局限）：明确写清本模式不判断范围、不追真问题、不保证事实准确、
  无中间信号、不做设计、不保证零错误。此前完全缺失——设计边界被外部评测读成了"主动性低"的能力缺陷。
- §二 新增 **失败模式 if-then 表**（工具不可用 / 命令报错 / 要等很久 / 上下文要爆 / 工具本身就慢），
  原「阻塞即换路」条款保留在表下方。
- §三 新增 **「省次数，不省范围」**：验证只跑一次，但这一次必须覆盖改动过的全部影响面。

### Fixed

- **验收账本会被压缩吃掉**：原文要求把条目「在心里或 todo 里列出来」，但本 preset 配了
  `thresholdRatio: 0.4` 自动压缩——长任务跑到一半账本先没了，而交付又要求逐条回执。
  改为强制 `todo_write` 落盘；条目 ≥5 时另落 `ledger-<任务>.md`（编号｜要求｜状态｜证据）。
- **两处相反处方**：§二「阻塞即换路，不许因此停下」与 §三「第二次失败停手」冲突，
  且「值得不值得修」全篇无定义。补三条硬判据：错误指向具体一个点 / 改动 1–3 行 / 不涉及生疏 API。
- **可打断情形由三种改为四种**：新增「按 §三 修复一次后仍失败」，堵住原先自相矛盾的缺口。
- **「零提问」名不副实**：原先一边写零提问、一边允许「冒出新的歧义」打断。
  改为「低提问」，明说四种口子，并禁止自称零提问。
- **5 秒规则与 `searchTimeoutMs: 60000` 冲突**：为 web_search 一类原生就慢的工具补例外行。

### 依据

用女娲（`huashu-nuwa` 1.1.0）方法论对人格做的独立评审（标准模式子代理、无上下文）结论：
骨架成立，但 P0 缺失败降级表与诚实边界，P1 验收账本只存在「心里」。
上述 Fixed 中「账本」「相反处方」「零提问命名」三项为该评审独有发现，v0.2 草案首版并未覆盖。

## [0.1.5] - 2026-11-07

### Added

- 人格「〇、指令遵循」把「服从」拆成三层，堵住静默造假的漏洞：
  - **事实层以实测为准**：任务书写的事实（数字/行数/字节/路径/存在性/命令可行性/当前状态）
    与实测不符，就地采用实测口径，并在回执里标出「任务书写 X，实测 Y」，不许为对上任务书硬凑数据。
    更正事实不是裁量——事实没有第二个选项，因此不构成对服从的削弱。
  - **决定层只能由用户改**：做什么、做多少、做到什么程度，只提不换。
  - **任务书之外的动作必须原样上报**：为了做完任务而必须做任务书没写的事（补文件、改第二处、
    装依赖、消断链），非破坏性且不花钱的直接做，破坏性/花钱的按第一节停手问；无论哪种都必须
    写清做了什么、改在哪、为什么、影响范围、回滚方案，一件都不许静默。
- 交付第三段「遗留与风险」明确要求原地列出任务书之外的补正（含回滚方案）。

### 依据

一次外部评测中发现：执行者在任务书给定的「改前 5813 字节」与实测 9755 冲突时，
选择了更正口径而非硬凑漂亮对比——行为正确，但当时的协议里没有任何条款要求它这么做，
纯属模型自身判断。本版把这条从「运气」变成「义务」。

## [0.1.4] - 2026-11-05

### Fixed

- 守卫误伤 `run_code`：0.1.3 把 `timeoutMs`（执行预算）也当成等待上限拦截，导致 `run_code`
  只要声明 20 秒预算就被拒绝、程序体根本不运行。实测子会话 `dbd87f82` 复现了这一点。
- 现在只拦「等待类」参数：
  - `wait: true`（任何工具）→ 拒绝；
  - `timeout_ms > maxWaitMs`（`job_output` / `wait_agent` 用的蛇形参数）→ 拒绝；
  - `timeoutMs`（`run_code` / `pwsh` 的执行预算）→ **不再限制**。

## [0.1.3] - 2026-11-05

### Added

- 新增自带守卫插件 `guard.js`（挂在本预设内）：把「不许同步等」从提示词变成运行时拒绝。
  任何工具调用只要带 `wait: true`，或 `timeout_ms` / `timeoutMs` 超过 `maxWaitMs`（默认 5000），
  直接被拒绝，并返回「改用 wait:false / 起后台作业」的改道提示。
- 人格新增「阻塞即换路」：发现某条路会堵（工具不可用、要等超过 5 秒、依赖卡住），
  立刻自己换一条更快的替代路径把任务做完，不许干等、不许停下、不许把「等」当解法。

### Fixed

- 实测事故：效率模式子会话用 `job_output(wait:true, timeout_ms:260000)` 同步阻塞 82.9 秒，
  随后 `run_code` 以 `CODE_RUN_FAILED` 失败。人格只写了「用 wait:false」却没有禁令，
  属于指令不够硬；本次同时补提示词禁令与运行时守卫。

## [0.1.2] - 2026-11-04

### Changed

- 新增人格第〇条「指令遵循（最高优先级）」：效率模式定位为**纯执行者**——不制定计划、
  不做设计、不改范围；任务书与计划表逐条执行，交付逐条回执（已做／未做＋原因＋证据），
  缺一条不许说「完成」。为了快而少做一条，比慢三倍更失败。
- 交付格式改为「结论一句／逐条回执／遗留与风险」：条目 ≥3 用表格，只有一条就一句话。
- 中英文 README 同步：人格从四条铁律扩为五条，指令遵循排第 0。

## [0.1.1] - 2026-11-04

### Fixed

- 人格补上「交付前零成本自检」：把任务书的每条要求逐项点过，只核对、不重做。
  A/B 实测（高中化学难度重排）中，效率模式因追求紧凑漏掉整块「化学反应与能量」，
  而标准模式靠更长的分层输出覆盖了 16 章。核对与「不重复验证」不冲突：
  验证是重做（仍禁止），核对是点数（成本几乎为零）。
- 人格补上列举类任务的清单纪律：任务书出现「全部 / 所有 / 完整 / 逐一 / 列出 / 排序」时，
  动笔前先把清单在心里列全；这类任务的失败几乎都是漏项而不是写错。
